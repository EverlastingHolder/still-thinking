# Development process

## Назначение

Общий порядок выполнения любой задачи в `Still Thinking`.

## 1. Классификация задачи

Определи тип:

- `feature` — новая пользовательская возможность;
- `fix` — исправление дефекта;
- `refactor` — изменение структуры без изменения поведения;
- `test` — тестовая инфраструктура или дополнительные проверки;
- `chore` — инфраструктура и конфигурация;
- `docs` — документация;
- `spike` — исследование без production-реализации.

Зафиксируй затронутые пользовательские сценарии, слои, модели данных, системные эффекты и необходимые проверки.

## 2. Изучение текущего состояния

Перед изменением кода:

1. Проверь текущую ветку и рабочее дерево.
2. Используй CodeGraph для поиска связанных файлов, символов, callers/callees и существующих реализаций.
3. Прочитай только релевантные файлы и тесты.
4. Определи Xcode project/workspace, scheme и targets из репозитория.
5. Проверь текущий этап в `docs/PRODUCT/IMPLEMENTATION_PLAN.md`.
6. Проверь, существует ли feature в `docs/PRODUCT/FEATURES.md`.
7. Проверь архитектурные границы в `docs/ARCHITECTURE/PROJECT_STRUCTURE.md`.
8. Если задача затрагивает логи, каналы или debug configuration, прочитай `docs/TECHNICAL/LOGGING.md`.

Не создавай второй паттерн, если в проекте уже есть подходящее решение.

## 3. План

Для значимого изменения сформулируй краткий план:

- цель;
- затрагиваемые области;
- изменения данных и контрактов;
- последовательность реализации;
- тестовая стратегия;
- способ Preview/Simulator-проверки;
- риски и неизвестные.

План должен разбивать крупную работу на шаги, после которых проект остаётся собираемым.

## 4. Реализация

- Выполняй минимальное изменение, достаточное для задачи.
- Не форматируй и не рефактори несвязанные области.
- Не дублируй бизнес-логику во View, persistence и service-слоях.
- Добавляй тесты одновременно с бизнес-логикой.
- Обновляй Preview одновременно с UI.
- Не скрывай ошибки и не подавляй Swift 6 diagnostics без обоснования.
- Сохраняй cancellation и actor isolation.
- Не добавляй зависимость или новый инфраструктурный слой без решения пользователя.
- Не добавляй `print`, `debugPrint` или прямой `OSLog.Logger` вне logging infrastructure.

## 5. Самопроверка

До запуска инструментов проверь:

- корректность empty/loading/error/content states;
- optional и error handling;
- отсутствие приватного текста в логах;
- возможность отключить новый шумный log channel;
- отсутствие повторного логирования одной ошибки на каждом слое;
- локализацию пользовательских строк;
- accessibility labels, Dynamic Type и tap targets;
- отсутствие test/preview data в production flow;
- соответствие файловой структуре проекта.

## 6. Проверки

Выполни применимые проверки в порядке:

1. SwiftLint.
2. Simulator build.
3. Swift Testing.
4. Preview через Xcode MCP/Canvas.
5. Ручной сценарий в Simulator.
6. Для logging-изменений — проверить включение и отключение каналов через Debug configuration.
7. Финальный `git diff`.

Если локальные применимые проверки прошли, не нужно ждать завершения GitHub CI test job перед итоговым отчётом, продолжением следующей задачи или передачей PR на review. В отчёте укажи, что локальные проверки пройдены, а CI не ожидался. Это правило не отменяет GitHub branch protection и не разрешает merge PR с незавершёнными или упавшими обязательными checks.

Подробности находятся в:

- `docs/WORKFLOW/TESTING.md`;
- `docs/WORKFLOW/XCODE_VALIDATION.md`;
- `docs/WORKFLOW/TOOLING.md`;
- `docs/TECHNICAL/LOGGING.md`.

## 7. Definition of Done

Кодовая задача завершена, когда:

- [ ] цель выполнена без несвязанных изменений;
- [ ] структура файлов соответствует правилам;
- [ ] Swift 6 strict concurrency не отключён и не обойдён небезопасно;
- [ ] SwiftLint пройден либо ограничение среды явно указано;
- [ ] приложение собирается для Simulator;
- [ ] новая/изменённая бизнес-логика покрыта Swift Testing;
- [ ] полный test target проходит;
- [ ] Preview обновлены и проверены, если применимо;
- [ ] пользовательский сценарий проверен в Simulator, если применимо;
- [ ] приватные данные не попали в логи или артефакты;
- [ ] новые logs используют scoped channel и могут быть отфильтрованы;
- [ ] документация обновлена, если изменились правила или поведение;
- [ ] итоговый отчёт перечисляет только фактически выполненные проверки.

## 8. Итоговый отчёт

```markdown
## Результат
Что изменено и какое поведение получено.

## Изменённые файлы
- `path/to/file.swift` — назначение изменения

## Проверки
- SwiftLint — passed / failed / not run
- Build — passed / failed / not run
- Swift Testing — passed / failed / not run
- Preview — просмотренные состояния или причина отсутствия проверки
- Simulator — пройденный сценарий и destination
- Logging — проверенные каналы/уровни, если применимо

## Ограничения и риски
Что не удалось проверить, TODO и решения пользователя.
```
