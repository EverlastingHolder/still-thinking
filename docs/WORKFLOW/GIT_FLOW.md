# Работа с Git по модели Git Flow

## Назначение веток

- `master` — стабильные версии приложения.
- `develop` — основная интеграционная ветка разработки.
- `feature/*` — новые функции.
- `fix/*` — обычные исправления.
- `refactor/*` — изменение структуры без изменения поведения.
- `test/*` — тестовая инфраструктура и тесты.
- `chore/*` — инструменты и конфигурация.
- `docs/*` — документация.
- `release/*` — подготовка версии.
- `hotfix/*` — срочное исправление версии из `master`.

Ветки `master` и `develop` являются постоянными. Их нельзя удалять, переименовывать, принудительно перемещать или переписывать. Подробная конфигурация GitHub находится в `docs/WORKFLOW/REPOSITORY_RULES.md`.

## Обычная разработка

Рабочая ветка создаётся от актуального `develop`:

```bash
git status --short --branch
git switch develop
git pull --ff-only
git switch -c feature/create-thought
```

Ветки `feature/*`, `fix/*`, `refactor/*`, `test/*`, `chore/*` и `docs/*` сливаются через Pull Request только в `develop`.

Прямые commit и push в `develop` и `master` запрещены.

## Работа с feature

1. Создать ветку от `develop`.
2. Реализовать одну законченную цель.
3. Выполнить проверки.
4. Открыть Pull Request в `develop`.
5. После merge удалить рабочую ветку.

Если работа слишком большая для одного понятного PR, её нужно разделить на несколько вертикальных законченных частей.

## Подготовка release

```bash
git switch develop
git pull --ff-only
git switch -c release/1.0.0
```

В `release/*` разрешены только:

- номер версии и сборки;
- заметки к выпуску;
- финальные исправления;
- локализация и метаданные;
- изменения CI/CD для выпуска.

Новые функции в `release/*` не добавляются.

После проверки:

1. Открыть PR `release/*` в `master`.
2. После merge создать tag версии.
3. Вернуть изменения release в `develop` отдельным merge или PR.
4. Удалить release-ветку только после обратного слияния.

## Срочный hotfix

```bash
git switch master
git pull --ff-only
git switch -c hotfix/1.0.1-notification-crash
```

После проверки:

1. Открыть PR `hotfix/*` в `master`.
2. Создать patch release и tag.
3. Обязательно вернуть hotfix в `develop`.
4. Удалить hotfix-ветку только после обратного слияния.

## Pull Request

Один PR решает одну цель.

- Заголовок и описание PR пишутся на русском языке.
- Review-комментарии и ответы пишутся на русском языке.
- Технические имена типов, API, файлов и команд сохраняются на английском языке.
- Используется шаблон `.github/pull_request_template.md`.
- PR содержит инструкцию ручной проверки и список реально выполненных проверок.
- Несвязанный рефакторинг и массовое форматирование запрещены.
- Все обсуждения должны быть разрешены до merge.

## Способ merge

Для обычных PR в `develop` предпочтителен Squash and merge.

Для `release/*` и `hotfix/*` допустим merge commit, чтобы сохранить границу ветки и упростить обратное слияние в `develop`.

Merge выполняется только по явной команде пользователя.

## Сообщения commit

Используется формат Conventional Commits, а описание результата пишется на русском языке:

```text
feat: добавить создание мысли
fix: исключить повторное планирование уведомления
test: покрыть переход просроченной мысли
docs: разделить документацию процесса разработки
chore: настроить SwiftLint
```

Один commit должен содержать один логический результат. Перед commit необходимо проверить staged diff. Секреты, DerivedData и generated-файлы не коммитятся.

## Запрещённые действия

Без явной команды пользователя запрещено:

- пушить напрямую в `master` или `develop`;
- создавать прямой commit в этих ветках через GitHub;
- сливать Pull Request;
- удалять или переименовывать `master` и `develop`;
- принудительно обновлять ветки;
- переписывать опубликованную историю;
- удалять удалённые ветки;
- выполнять reset с потерей изменений;
- массово удалять untracked-файлы.
