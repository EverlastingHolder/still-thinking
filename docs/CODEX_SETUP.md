# Codex setup и ведение AGENTS.md

## Назначение

Этот документ объясняет, как в репозитории `still-thinking` организованы инструкции для Codex и как проверять их загрузку.

Официальная документация OpenAI:

- https://developers.openai.com/codex/guides/agents-md

## Как Codex находит инструкции

При запуске Codex один раз строит цепочку инструкций.

### Глобальный уровень

В каталоге Codex home, обычно `~/.codex`, проверяется:

1. `AGENTS.override.md`;
2. если override отсутствует — `AGENTS.md`.

На глобальном уровне используется первый непустой файл.

Глобальный файл подходит для личных правил, применимых ко всем репозиториям. Проектные технологии и команды не должны храниться только в глобальном файле.

### Уровень проекта

Codex начинает с корня Git-репозитория и идёт к текущей рабочей директории. В каждом каталоге он ищет:

1. `AGENTS.override.md`;
2. `AGENTS.md`;
3. дополнительные fallback-имена, только если они настроены в Codex config.

В одном каталоге загружается не более одного instruction-файла.

### Приоритет

Инструкции объединяются от корня к текущей директории. Файл, расположенный ближе к рабочей директории, имеет более высокий приоритет, потому что добавляется позже.

Поэтому:

- корневой `AGENTS.md` содержит общие правила проекта;
- вложенный `AGENTS.md` должен содержать только правила конкретной области;
- `AGENTS.override.md` используется только когда базовые правила действительно нужно заменить.

## Текущая структура репозитория

```text
AGENTS.md

docs/
├── CODEX_SETUP.md
└── DEVELOPMENT_WORKFLOW.md
```

Codex автоматически читает корневой `AGENTS.md`.

Корневой файл явно требует прочитать `docs/DEVELOPMENT_WORKFLOW.md`, потому что обычные Markdown-документы не становятся системными инструкциями только из-за наличия в `docs/`.

`docs/CODEX_SETUP.md` предназначен для разработчика и обслуживания конфигурации. Его не требуется читать перед каждой кодовой задачей.

## Почему AGENTS.md остаётся компактным

OpenAI указывает, что суммарный размер проектных инструкций ограничен параметром `project_doc_max_bytes`; значение по умолчанию — 32 KiB.

Поэтому в `AGENTS.md` хранятся:

- обязательный стек;
- архитектурные ограничения;
- запреты;
- обязательные проверки;
- основные Git-правила;
- формат итогового отчёта.

Подробные объяснения, сценарии и шаблоны команд вынесены в `docs/DEVELOPMENT_WORKFLOW.md`.

Не следует копировать в `AGENTS.md` полное техническое задание, продуктовую концепцию или длинный roadmap.

## Когда создавать вложенный AGENTS.md

Вложенный файл нужен, если у области появляются отличающиеся правила, например:

```text
Services/Notifications/AGENTS.md
Features/Reflection/AGENTS.md
```

Примеры оправданных локальных правил:

- отдельный набор обязательных тестов для notification scheduling;
- запрет на использование реального `UNUserNotificationCenter` в Preview;
- специальные migration-проверки для persistence-слоя;
- дополнительные privacy-ограничения.

Не создавать вложенный файл, если он только повторяет корневые правила.

## Когда использовать AGENTS.override.md

Override-файл полностью имеет приоритет над обычным `AGENTS.md` в том же каталоге.

Использовать его только для:

- временной экспериментальной политики;
- изолированного automation-профиля;
- области, где базовые инструкции действительно должны быть заменены, а не дополнены.

Не использовать `AGENTS.override.md` как постоянный скрытый способ обхода проектных требований.

## Проверка загрузки инструкций

Из корня репозитория:

```bash
codex --ask-for-approval never "Summarize the current instructions."
```

Ожидается, что Codex перечислит правила из глобального файла, если он существует, а затем из корневого `AGENTS.md`.

Для проверки инструкций в подкаталоге:

```bash
codex --cd <subdirectory> --ask-for-approval never \
  "Show which instruction files are active."
```

Codex должен показать корневой файл и вложенную инструкцию, если она существует.

Дополнительно проверить:

```bash
codex status
```

Workspace root должен совпадать с корнем `still-thinking`.

## Проверка через лог

Для аудита загруженных инструкций можно запустить Codex с plaintext TUI log:

```bash
codex -c log_dir=./.codex-log
```

Затем проверить:

```text
.codex-log/codex-tui.log
```

Каталог `.codex-log/` не должен попадать в Git.

## Обновление инструкций

Codex строит цепочку инструкций при каждом новом запуске или при старте новой TUI-сессии.

После изменения `AGENTS.md`:

1. завершить текущую Codex-сессию;
2. запустить новую из нужной директории;
3. выполнить команду суммаризации инструкций;
4. убедиться, что новые правила загружены.

Отдельная очистка кэша не требуется.

## Правила изменения AGENTS.md

При обновлении файла:

1. Добавлять только правила, которые должны применяться почти к каждой задаче.
2. Использовать конкретные команды и проверяемые требования.
3. Не писать расплывчатые указания вроде «пиши качественный код».
4. Не дублировать длинные разделы из других документов.
5. Не ссылаться на несуществующий путь.
6. После изменения проверять размер и фактическую загрузку файла.
7. Если правило относится к одной области, переносить его во вложенный `AGENTS.md`.
8. Если правило временное, не превращать его в постоянную норму.
9. При изменении build/test flow синхронно обновлять `docs/DEVELOPMENT_WORKFLOW.md`.

## Проверка размера

```bash
wc -c AGENTS.md
find . -name 'AGENTS.md' -o -name 'AGENTS.override.md'
```

При приближении совокупного объёма к лимиту:

- сократить дублирование;
- вынести подробности в обычные документы;
- создать локальные инструкции только в нужных каталогах;
- менять `project_doc_max_bytes` только осознанно.

## Локальная глобальная инструкция

При необходимости можно создать личный файл:

```text
~/.codex/AGENTS.md
```

Там допустимы общие предпочтения, например:

- язык итогового отчёта;
- необходимость всегда показывать выполненные команды;
- запрет на установку инструментов без подтверждения.

Проектные правила `still-thinking` должны оставаться в репозитории, чтобы они одинаково применялись на других машинах и у других участников.
