# Development Workflow

## 1. Назначение документа

Этот документ определяет обязательный процесс разработки `Still Thinking` для человека и Codex:

- порядок выполнения задач;
- работу с Git;
- требования к SwiftUI Preview;
- проверку приложения в iOS Simulator;
- работу с тестами на Swift Testing;
- минимальные quality gates перед завершением задачи;
- формат отчёта о выполненной работе.

Корневой `AGENTS.md` содержит краткие обязательные правила. Этот документ раскрывает их подробно. При конфликте требований применяется более строгое правило, если пользователь явно не указал обратное.

---

## 2. Базовые принципы

1. **Сначала понять задачу, затем менять код.**
2. **Одна задача — одна цель — одна ветка.**
3. **Минимальное изменение предпочтительнее широкого рефакторинга.**
4. **Компиляция не доказывает корректность поведения.**
5. **Preview не заменяет запуск приложения.**
6. **Запуск в Simulator не заменяет тесты.**
7. **Тесты не заменяют ручную проверку изменённого пользовательского сценария.**
8. **Нельзя заявлять о проверке, которая фактически не выполнялась.**
9. **Содержание пользовательских мыслей не должно попадать в логи, тестовые отчёты, скриншоты и telemetry.**
10. **Любая новая production-зависимость требует отдельного согласования.**

---

## 3. Источники требований

Перед началом задачи Codex должен проверить инструкции в следующем порядке:

1. Явная формулировка текущей задачи пользователя.
2. `AGENTS.md` в корне репозитория.
3. Этот документ.
4. Продуктовые и технические документы в `docs/`.
5. Существующий код, тесты и принятые паттерны проекта.

Нельзя заменять требования догадками. Если имя проекта, схемы, target, bundle identifier или минимальная версия iOS уже определены в репозитории, используются фактические значения.

На этапе первоначального bootstrap рекомендуемые имена:

- Xcode project: `StillThinking.xcodeproj`;
- app target: `StillThinking`;
- shared scheme: `StillThinking`;
- test target на Swift Testing: `StillThinkingTests`.

После создания проекта источником истины становятся настройки Xcode project.

# Часть I. Рабочий цикл задачи

## 4. Этап 0 — классификация задачи

До изменения файлов определить тип задачи:

- `feature` — новая пользовательская возможность;
- `fix` — исправление дефекта;
- `refactor` — изменение структуры без изменения поведения;
- `chore` — инфраструктура, конфигурация, инструменты;
- `test` — тестовая инфраструктура или дополнительные тесты;
- `docs` — документация;
- `spike` — исследование без production-реализации.

Также определить:

- какие пользовательские сценарии затрагиваются;
- какие слои затрагиваются;
- требуется ли изменение persistence-схемы;
- требуется ли обновление уведомлений;
- требуется ли Preview;
- какие тесты должны появиться или измениться;
- как сценарий будет проверен в Simulator.

## 5. Этап 1 — изучение репозитория

Перед реализацией:

1. Проверить `git status`.
2. Определить текущую ветку.
3. Найти Xcode project или workspace.
4. Определить shared scheme и targets.
5. Прочитать связанные модели, View, services и тесты.
6. Найти существующие аналоги, чтобы не создавать второй паттерн для той же задачи.
7. Проверить конфигурацию SwiftLint.
8. Проверить доступные команды CI, scripts или Makefile, если они существуют.

Полезные команды:

```bash
git status --short --branch
find . -maxdepth 3 \( -name "*.xcworkspace" -o -name "*.xcodeproj" \)
```

Если найден workspace, для команд сборки предпочитать workspace. Если workspace отсутствует, использовать project.

Список схем необходимо получать из проекта, а не угадывать:

```bash
xcodebuild -list -workspace <Workspace>.xcworkspace
# или
xcodebuild -list -project <Project>.xcodeproj
```

## 6. Этап 2 — план

Перед значимыми изменениями составить краткий план:

- цель;
- изменяемые файлы/модули;
- изменения модели данных;
- тестовая стратегия;
- способ проверки UI;
- риски и неизвестные.

Для небольшой правки план может состоять из 2–4 пунктов. Для сложной фичи план разбивается на независимые шаги, каждый из которых оставляет проект в собираемом состоянии.

## 7. Этап 3 — реализация

Во время реализации:

- не менять несвязанные файлы;
- не форматировать весь проект из-за локальной правки;
- не переименовывать публичные типы без необходимости;
- сохранять обратную совместимость persistence-схемы либо явно описывать миграцию;
- внедрять время, UUID и системные эффекты;
- учитывать cancellation и actor isolation;
- писать пользовательские строки через механизм локализации, когда инфраструктура локализации уже создана;
- обновлять Preview одновременно с изменением UI;
- добавлять тесты одновременно с бизнес-логикой, а не после завершения всей фичи.

После каждого логически законченного шага проект должен компилироваться либо Codex должен явно указать, почему временно не компилируется.

## 8. Этап 4 — локальная самопроверка кода

Перед запуском инструментов:

- проверить обработку ошибок;
- проверить optional-состояния;
- проверить empty/loading/error/content states, если они применимы;
- проверить Swift 6 isolation;
- проверить отсутствие пользовательских данных в `print`, OSLog и diagnostics;
- проверить доступность интерфейса: labels, Dynamic Type, достаточные tap targets;
- проверить, что тестовые данные не попали в production flow.

## 9. Этап 5 — автоматические и визуальные проверки

Проверки выполняются в следующем порядке:

1. SwiftLint.
2. Build для iOS Simulator.
3. Swift Testing.
4. SwiftUI Preview для изменённых представлений.
5. Ручной пользовательский сценарий в Simulator.
6. Финальная проверка Git diff.

Если ранний этап не пройден, исправить проблему до перехода дальше. Если исправление невозможно в текущем окружении, не скрывать это и продолжить только те проверки, которые остаются достоверными.

## 10. Этап 6 — итоговый отчёт

Codex должен сообщить:

- краткое описание реализации;
- список основных затронутых файлов;
- выполненные команды;
- результаты lint/build/tests;
- проверенные Preview и состояния;
- пройденный сценарий в Simulator;
- ограничения среды;
- оставшиеся риски и TODO.

# Часть II. Git workflow

## 11. Основная модель ветвления

Используется упрощённый trunk-based flow с короткоживущими ветками.

Основная ветка:

```text
master
```

После первоначального bootstrap запрещено вести обычную разработку напрямую в `master`.

Форматы веток:

```text
feature/<short-description>
fix/<short-description>
refactor/<short-description>
chore/<short-description>
test/<short-description>
docs/<short-description>
spike/<short-description>
```

Примеры:

```text
feature/create-thought
fix/reschedule-notification
test/return-scheduler
chore/configure-swiftlint
```

Если задача привязана к issue, номер можно добавить:

```text
feature/12-create-thought
```

## 12. Создание ветки

Перед созданием ветки:

```bash
git status --short --branch
git switch master
git pull --ff-only
```

Затем:

```bash
git switch -c feature/create-thought
```

Codex не должен выполнять `git pull`, переключать ветку или перезаписывать локальные изменения, если рабочее дерево не чистое и эти изменения не принадлежат текущей задаче.

## 13. Коммиты

Используется Conventional Commits:

```text
<type>: <imperative summary>
```

Допустимые типы:

- `feat`
- `fix`
- `refactor`
- `test`
- `docs`
- `chore`
- `build`
- `ci`

Примеры:

```text
feat: add thought creation flow
fix: reschedule pending local notification
test: cover overdue thought transition
chore: configure SwiftLint
```

Требования:

- один коммит содержит одну логическую часть;
- сообщение описывает результат, а не процесс;
- нельзя использовать сообщения `update`, `fix stuff`, `changes`;
- generated-файлы и DerivedData не коммитятся;
- перед коммитом проверить staged diff;
- тесты и реализация одной бизнес-правки обычно находятся в одном коммите, если разделение не улучшает ревью.

Codex не создаёт коммит, push или pull request, если пользователь просил только анализ, документ или план. Push, merge, force push и удаление веток выполняются только по явному указанию.

## 14. Pull request

Один PR должен:

- иметь одну понятную цель;
- быть достаточно небольшим для полноценного ревью;
- не содержать несвязанный рефакторинг;
- включать тесты для изменённой бизнес-логики;
- включать визуальные материалы для заметных UI-изменений, когда это возможно;
- описывать фактически выполненные проверки.

Рекомендуемая структура PR:

```markdown
## Что изменено

## Почему

## Как проверить

## Выполненные проверки
- [ ] SwiftLint
- [ ] Simulator build
- [ ] Swift Testing
- [ ] Preview
- [ ] Manual Simulator flow

## Риски / ограничения
```

## 15. Запрещённые Git-операции без прямой команды

- `git push --force` и `--force-with-lease`;
- rebase общей/удалённой ветки;
- reset с потерей пользовательских изменений;
- merge в `master`;
- удаление remote branch;
- изменение истории опубликованных коммитов;
- массовое удаление untracked-файлов;
- добавление секретов или signing credentials.

# Часть III. SwiftLint

## 16. Правила использования

SwiftLint обязателен для проекта.

Базовая команда:

```bash
swiftlint lint --strict
```

Если в репозитории появится script, Makefile или CI-команда, она становится предпочтительным способом запуска.

Codex не должен автоматически устанавливать или обновлять SwiftLint без разрешения. Если `swiftlint` отсутствует:

1. сообщить об этом;
2. не считать lint выполненным;
3. продолжить build/tests, если они доступны;
4. предложить конкретный способ установки отдельно.

Нельзя отключать правило только для прохождения lint. Локальный `swiftlint:disable` допустим лишь при объективной причине и с коротким комментарием.

# Часть IV. Сборка и iOS Simulator

## 17. Определение доступного Simulator

Нельзя жёстко предполагать модель iPhone или версию iOS.

Сначала получить destinations:

```bash
xcodebuild -showdestinations \
  -project <Project>.xcodeproj \
  -scheme <Scheme>
```

При необходимости:

```bash
xcrun simctl list devices available
```

Предпочтение:

1. уже загруженный совместимый iPhone Simulator;
2. доступный iPhone с наиболее новой установленной runtime;
3. фиксированный CI destination, когда он определён workflow-файлом.

Использовать destination по `id`, чтобы избежать неоднозначности:

```text
platform=iOS Simulator,id=<SIMULATOR_UDID>
```

## 18. Simulator build

Шаблон команды для project:

```bash
xcodebuild build \
  -project <Project>.xcodeproj \
  -scheme <Scheme> \
  -configuration Debug \
  -destination 'platform=iOS Simulator,id=<SIMULATOR_UDID>' \
  CODE_SIGNING_ALLOWED=NO
```

Для workspace:

```bash
xcodebuild build \
  -workspace <Workspace>.xcworkspace \
  -scheme <Scheme> \
  -configuration Debug \
  -destination 'platform=iOS Simulator,id=<SIMULATOR_UDID>' \
  CODE_SIGNING_ALLOWED=NO
```

Нельзя считать сборку успешной только потому, что отдельный Swift-файл не показывает ошибок в редакторе.

## 19. Ручная проверка в Simulator

Для любого изменения, влияющего на пользовательское поведение:

1. Запустить приложение на доступном Simulator.
2. Перейти к изменённому сценарию обычным пользовательским путём.
3. Проверить основной сценарий.
4. Проверить минимум один граничный или ошибочный сценарий.
5. Перезапустить приложение, если затронуто persistence или восстановление состояния.
6. Проверить светлую и тёмную тему для заметного UI-изменения.
7. Проверить крупный Dynamic Type для нового экрана или сложного компонента.
8. Проверить отсутствие утечки приватного текста в уведомления, логи и application switcher, если изменение касается приватности.

Для базовых продуктовых фич рекомендуется проверять:

- пустой архив;
- создание мысли;
- повторное открытие сохранённой мысли;
- просроченное возвращение;
- добавление reflection;
- повторное откладывание;
- завершение или отпускание мысли;
- поведение при запрещённых уведомлениях.

## 20. Что делать, если Simulator недоступен

Codex должен:

- выполнить доступные lint/build/tests;
- указать точную причину, почему Simulator не запущен;
- не писать, что UI или сценарий проверены;
- дать короткую инструкцию для ручной проверки разработчиком.

# Часть V. SwiftUI Preview

## 21. Когда Preview обязателен

Добавлять или обновлять `#Preview`, если изменяется:

- экран;
- переиспользуемый компонент с заметным поведением;
- компонент с несколькими состояниями;
- layout, зависящий от текста, темы или Dynamic Type;
- timeline/карточка мысли/форма ввода;
- empty, loading, error или content state.

Preview не обязателен для простого private-компонента без собственного состояния, если он уже покрыт Preview родительского экрана.

## 22. Требования к Preview

Preview должен:

- собираться;
- использовать фиксированное время и детерминированные UUID;
- использовать sample/fake dependencies;
- использовать in-memory SwiftData container, если требуется persistence;
- не планировать реальные уведомления;
- не вызывать LocalAuthentication;
- не зависеть от сети;
- не менять production-данные;
- демонстрировать реалистичные, но не реальные пользовательские данные.

Рекомендуемые состояния:

```text
Empty
Typical content
Long text
Validation/error
Dark mode
Large Dynamic Type
```

Не нужно создавать отдельный Preview для каждой незначительной комбинации. Набор должен покрывать риски layout и состояния.

## 23. Проверка Preview

Для изменённых Preview:

1. Убедиться, что target компилируется.
2. Открыть Preview в Xcode, если среда предоставляет управление Xcode/Canvas.
3. Проверить отсутствие crash и явных layout-проблем.
4. Проверить длинный текст и локализацию, если они влияют на layout.

Если Codex не имеет доступа к Xcode Canvas, он обязан прямо указать это. В таком случае:

- Preview остаётся в коде и должен компилироваться;
- визуальная проверка переносится в Simulator;
- итоговый отчёт не должен утверждать, что Canvas был просмотрен.

# Часть VI. Тесты

## 24. Тестовый фреймворк

Для unit- и integration-тестов используется только Swift Testing:

```swift
import Testing

@Suite("Return scheduler")
struct ReturnSchedulerTests {
    @Test("Marks an overdue thought as returned")
    func marksOverdueThoughtAsReturned() async throws {
        // Arrange
        // Act
        // Assert
        #expect(true)
    }
}
```

Использовать:

- `@Suite` для осмысленной группировки;
- `@Test` с описанием поведения;
- `#expect` для обычных проверок;
- `#require` для обязательных preconditions теста;
- parameterized tests для таблиц входных данных;
- tags/traits только когда они улучшают фильтрацию и CI.

XCTest не используется для unit- и integration-тестов.

XCUITest/UI automation не входит в обязательный MVP, поскольку основан на XCTest. Его добавление требует отдельного решения и обновления технических правил. До этого UI проверяется через Preview и ручные сценарии в Simulator.

## 25. Что тестировать обязательно

Тесты обязательны для:

- переходов `ThoughtStatus`;
- определения просроченных возвращений;
- создания, переноса и отмены `ReturnSchedule`;
- выбора reflection prompt;
- завершения и отпускания цепочки;
- repository mapping;
- migration/persistence behavior;
- защиты от дублирующего планирования уведомлений;
- обработки смены даты/часового пояса, когда такая логика появится;
- каждого исправленного дефекта, если он воспроизводим детерминированно.

## 26. Требования к тестам

Тест должен быть:

- детерминированным;
- независимым от порядка запуска;
- независимым от реальных уведомлений и биометрии;
- независимым от текущей даты;
- быстрым;
- читаемым как описание поведения.

Запрещено:

- `sleep` для ожидания асинхронной логики;
- зависимость от локальной таймзоны без явного задания;
- shared mutable global state;
- использование production SwiftData store;
- обращения к реальным системным permission dialogs;
- утверждения только ради достижения coverage.

## 27. Тестовые зависимости

Для тестируемой логики должны существовать controllable dependencies:

- `Clock` / фиксированное текущее время;
- UUID generator;
- notification scheduling client;
- authentication client;
- in-memory repository или ModelContainer;
- logger sink без приватного текста.

Тестовая абстракция должна соответствовать реальной границе эффекта. Не создавать протокол на каждый тип без необходимости.

## 28. Запуск тестов

Шаблон:

```bash
xcodebuild test \
  -project <Project>.xcodeproj \
  -scheme <Scheme> \
  -destination 'platform=iOS Simulator,id=<SIMULATOR_UDID>' \
  CODE_SIGNING_ALLOWED=NO
```

Для workspace заменить `-project` на `-workspace`.

При падении теста:

1. определить первый причинный failure;
2. не обновлять expectation вслепую;
3. проверить, является ли проблема production-дефектом, недетерминированностью или неверным тестом;
4. исправить причину;
5. повторно запустить как минимум затронутый suite;
6. перед завершением выполнить полный test target.

## 29. Тестирование исправления дефекта

Предпочтительный flow:

1. Воспроизвести дефект.
2. Добавить тест, который падает по ожидаемой причине.
3. Внести минимальное исправление.
4. Убедиться, что новый тест проходит.
5. Запустить связанные suites.
6. Запустить полный набор тестов.
7. Проверить пользовательский сценарий в Simulator, если дефект видим пользователю.

Если дефект нельзя воспроизвести unit/integration-тестом, описать причину и подготовить ручной regression scenario.

# Часть VII. Definition of Done

## 30. Общий DoD для кодовой задачи

Задача считается завершённой, когда:

- [ ] Реализация соответствует поставленной цели.
- [ ] Нет несвязанных изменений.

# Часть IX. Развитие инструкции

Корневой `AGENTS.md` должен оставаться компактным. Если отдельная область проекта получит специфические правила, допускается добавить вложенный `AGENTS.md` рядом с этой областью, например:

```text
Features/Reflection/AGENTS.md
Services/Notifications/AGENTS.md
```

Вложенные инструкции должны описывать только локальные отличия и не дублировать весь корневой файл.

`AGENTS.override.md` используется только для временной или действительно заменяющей инструкции. Он не должен оставаться в репозитории как скрытый постоянный способ отменить базовые правила.

При изменении build/test-команд, структуры проекта или Git flow необходимо одновременно обновлять этот документ и `AGENTS.md`, если краткие обязательные правила также изменились.
