# AGENTS.md

## Назначение

Этот файл содержит обязательные инструкции для Codex и других coding agents, работающих в репозитории `still-thinking`.

Перед любыми изменениями:

1. Прочитай этот файл полностью.
2. Прочитай `docs/DEVELOPMENT_WORKFLOW.md`.
3. Изучи затронутые файлы и существующие тесты.
4. Сформулируй краткий план до начала значимых изменений.
5. Не делай предположений о структуре проекта, схеме Xcode, bundle identifier или доступных симуляторах — сначала определи их из репозитория и локального окружения.

## Продукт

`Still Thinking` — локальное iOS-приложение для фиксации незавершённых мыслей, их отложенного возвращения и последующего переосмысления.

Основной пользовательский цикл:

`записать → отложить → получить возвращение → ответить → завершить или отложить снова`.

Изменения, не усиливающие этот цикл, не должны добавляться без отдельного решения.

## Обязательный технический стек

- Swift 6.
- SwiftUI.
- SwiftData.
- Observation (`@Observable`).
- Swift Concurrency со strict concurrency checking.
- Swift Testing (`import Testing`, `@Suite`, `@Test`, `#expect`).
- SwiftLint.
- UserNotifications для локальных уведомлений.
- LocalAuthentication для локальной блокировки приложения.
- OSLog без пользовательского содержимого.

## Запрещено без явного согласования

- Добавлять production-зависимости или SDK.
- Добавлять backend, авторизацию, Firebase, аналитику, CloudKit или сетевой слой.
- Использовать XCTest для unit- и integration-тестов.
- Добавлять XCUITest/UI-test target: XCUITest основан на XCTest и требует отдельного решения.
- Отключать Swift 6 strict concurrency ради устранения ошибок компиляции.
- Использовать `@unchecked Sendable`, `nonisolated(unsafe)` или подавление предупреждений без документированного обоснования.
- Хранить текст мыслей, ответов или поисковых запросов в логах.
- Делать массовый рефакторинг вне текущей задачи.
- Менять архитектурные границы, deployment target или публичные контракты без отдельного согласования.
- Коммитить секреты, signing credentials, пользовательские данные, DerivedData и локальные настройки Xcode.

## Архитектурные правила

- Структура ориентирована на feature-модули и слои `Domain`, `Data`, `Services`, `DesignSystem`.
- SwiftUI View отвечает за отображение и отправку пользовательских действий.
- Состояние экрана размещается в `@Observable` model/view model.
- Бизнес-правила размещаются в use case/domain-типах, а не во View.
- Хранилище скрыто за repository-протоколом.
- Время, UUID, уведомления, биометрия и другие внешние эффекты должны внедряться через зависимости.
- Не использовать `Date.now`, случайные UUID и реальные уведомления в детерминированных тестах.
- Не вводить абстракцию только ради абстракции. Каждый протокол должен иметь тестовую или архитектурную причину.

## Правила реализации

- Делай минимальное изменение, достаточное для выполнения задачи.
- Сохраняй существующий стиль и именование.
- Не дублируй бизнес-логику между View, model и persistence-слоем.
- Все новые async API должны быть корректны для Swift 6 isolation и cancellation.
- Не скрывай ошибки через пустой `catch`.
- Пользовательские тексты должны быть готовы к локализации; не разбрасывай строки по бизнес-логике.
- Для SwiftUI-компонентов с нетривиальным состоянием добавляй или обновляй `#Preview`.
- Preview должен использовать детерминированные данные и не обращаться к production-хранилищу, уведомлениям или биометрии.

## Тестирование

Для новой или изменённой бизнес-логики:

- добавь или обнови тесты на Swift Testing;
- для исправления дефекта по возможности сначала воспроизведи его тестом;
- проверь happy path, важные граничные случаи и переходы состояния;
- используй in-memory persistence и fake-зависимости;
- не используй произвольные задержки и `sleep` как средство синхронизации теста.

Preview и ручная проверка в симуляторе не заменяют unit/integration-тесты.

## Обязательная проверка изменений

Перед завершением задачи выполни применимые проверки в таком порядке:

1. `swiftlint`.
2. Сборка выбранной схемы для доступного iOS Simulator.
3. Тесты через `xcodebuild test` на доступном симуляторе.
4. Для UI-изменений — проверка соответствующих `#Preview`.
5. Для пользовательского сценария — запуск приложения в симуляторе и ручное прохождение изменённого потока.
6. Проверка `git diff` на случайные изменения, секреты и generated-файлы.

Не утверждай, что проверка выполнена, если команда не запускалась или результат не был доступен. В итоговом отчёте перечисли фактически выполненные команды, результат и ограничения.

## Git

- Основная ветка: `master`.
- После bootstrap не работай напрямую в `master`.
- Используй короткоживущие ветки:
  - `feature/<краткое-имя>`
  - `fix/<краткое-имя>`
  - `chore/<краткое-имя>`
  - `docs/<краткое-имя>`
- Одна ветка и один pull request должны решать одну цель.
- Коммиты должны быть небольшими и логически целостными.
- Формат сообщений: Conventional Commits, например `feat: add thought creation flow`.
- Не выполняй force push, merge, rebase общей ветки, удаление веток или публикацию изменений без явной команды пользователя.
- Не коммить и не отправляй изменения, если задача просит только анализ или план.

Полные правила рабочего процесса, Git, симулятора, Preview и тестов находятся в `docs/DEVELOPMENT_WORKFLOW.md`.

## Формат итогового отчёта Codex

После работы сообщи:

1. Что изменено.
2. Какие файлы затронуты.
3. Какие проверки реально выполнены и их результат.
4. Что не удалось проверить и почему.
5. Остались ли риски, TODO или решения, требующие подтверждения.

Не скрывай ошибки, неполные проверки и отклонения от требований.
