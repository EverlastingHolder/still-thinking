# AGENTS.md

## Назначение

Обязательные инструкции для Codex и других агентов разработки в репозитории `still-thinking`.

Перед изменениями:

1. Прочитай этот файл полностью.
2. Прочитай `docs/DEVELOPMENT_WORKFLOW.md` как индекс обязательных документов.
3. Изучи задачу, связанные файлы, зависимости и тесты.
4. Сформулируй краткий план до значимых изменений.
5. Не угадывай структуру проекта, схему Xcode, bundle identifier, доступный Simulator или команды сборки — определи их из репозитория и окружения.

## Язык проекта

- Вся документация в репозитории пишется на русском языке.
- Комментарии и документирующие комментарии в коде пишутся на русском языке.
- Описания Pull Request, Issue, review-комментарии и итоговые отчёты пишутся на русском языке.
- Отображаемые названия тестов Swift Testing пишутся на русском языке.
- Идентификаторы Swift, имена типов, методов, файлов, каталогов, веток, параметры API и общепринятые технические названия остаются на английском языке.
- Не добавляй комментарий, если код понятен без него. Комментарий должен объяснять причину, ограничение или неочевидное решение, а не пересказывать код.

## Продукт

`Still Thinking` — локальное iOS-приложение для фиксации незавершённых мыслей, их отложенного возвращения и последующего переосмысления.

Основной цикл:

`записать → отложить → получить возвращение → ответить → завершить или отложить снова`.

Новые функции должны соответствовать `docs/PRODUCT/FEATURES.md` и текущему этапу из `docs/PRODUCT/IMPLEMENTATION_PLAN.md`.

## Обязательный стек

- Swift 6.
- SwiftUI.
- SwiftData.
- Observation (`@Observable`).
- Swift Concurrency со строгой проверкой конкурентности.
- Swift Testing (`import Testing`, `@Suite`, `@Test`, `#expect`, `#require`).
- SwiftLint.
- UserNotifications.
- LocalAuthentication.
- OSLog без пользовательского содержимого.

Подробные технические ограничения: `docs/TECHNICAL/TECHNICAL_RULES.md`.

## Обязательные инструменты

### CodeGraph

Для навигации по коду, поиска файлов, символов, связей, вызывающих и вызываемых функций и оценки области влияния сначала используй CodeGraph MCP, если он доступен.

Не начинай с широкого `grep`, `find` или чтения большого числа файлов вслепую. Поиск через CLI допустим как резервный вариант, если CodeGraph недоступен, не проиндексировал проект или не возвращает нужный результат.

### Xcode MCP

Для SwiftUI Preview, диагностик Xcode, Canvas и интерактивной проверки через Simulator используй соответствующий Xcode MCP, если он доступен.

Команды `xcodebuild` и `simctl` остаются обязательным воспроизводимым способом сборки и тестирования и резервным вариантом при недоступности MCP.

Полные правила инструментов: `docs/WORKFLOW/TOOLING.md`.

## Архитектура и файлы

- Физическая структура каталогов должна соответствовать `docs/ARCHITECTURE/PROJECT_STRUCTURE.md`.
- Не создавай каталоги `Helpers`, `Managers`, `Common` или `Utils` без конкретной узкой ответственности.
- Один основной публичный тип — один файл; имя файла соответствует типу.
- Feature не должен зависеть от presentation-слоя другого feature.
- Бизнес-правила не размещаются во View.
- Persistence-типы не должны становиться доменными моделями напрямую.
- Время, UUID, уведомления, биометрия и другие эффекты внедряются через зависимости.
- Не создавай протокол или слой без тестовой либо архитектурной причины.

## Запрещено без явного согласования

- Добавлять production-зависимости, SDK, backend, авторизацию, Firebase, CloudKit, аналитику или сетевой слой.
- Использовать XCTest для unit- и integration-тестов.
- Добавлять XCUITest target.
- Отключать строгую проверку Swift Concurrency ради устранения ошибок.
- Использовать `@unchecked Sendable`, `nonisolated(unsafe)` или подавление диагностики без документированного обоснования.
- Логировать текст мыслей, ответов, поисковых запросов или другое приватное содержимое.
- Делать массовый рефакторинг вне текущей задачи.
- Менять deployment target, архитектурные границы, persistence-схему или публичные контракты без отдельного решения.
- Коммитить секреты, signing credentials, пользовательские данные, DerivedData и локальные настройки Xcode.

## Логирование

- Все постоянные логи проходят через проектный `LoggerClient`; `print`, `debugPrint` и прямое создание `OSLog.Logger` внутри feature, data и services запрещены.
- Logger должен быть привязан к стабильному каналу, который можно включить или отключить конфигурацией.
- Для изменений logging infrastructure, каналов, уровней или debug-переключателей обязательно прочитай `docs/TECHNICAL/LOGGING.md`.

## Git Flow и защищённые ветки

- `master` — стабильная release-ветка.
- `develop` — основная интеграционная и рабочая ветка.
- Обычные ветки `feature/*`, `fix/*`, `chore/*`, `docs/*`, `test/*` и `refactor/*` создаются от `develop` и сливаются обратно в `develop` только через Pull Request.
- `release/*` создаётся от `develop`, сливается в `master`, после чего изменения возвращаются в `develop`.
- `hotfix/*` создаётся от `master`, сливается в `master` и обязательно обратно в `develop`.
- Прямые push и commit в `master` и `develop` запрещены.
- Ветки `master` и `develop` запрещено удалять, переименовывать, принудительно перемещать или переписывать.
- Не выполняй merge, push, force push, rebase опубликованной ветки или удаление удалённых веток без явной команды пользователя.

Полные правила: `docs/WORKFLOW/GIT_FLOW.md` и `docs/WORKFLOW/REPOSITORY_RULES.md`.

## Реализация

- Делай минимальное изменение, достаточное для задачи.
- Сохраняй существующее именование и архитектурные границы.
- Не скрывай ошибки через пустой `catch`.
- Все async API должны учитывать isolation и cancellation.
- Пользовательские строки должны быть готовы к локализации.
- Для изменённых SwiftUI-экранов и нетривиальных компонентов добавляй или обновляй `#Preview`.
- Preview использует детерминированные данные и не вызывает production-хранилище, реальные уведомления, сеть или биометрию.

## Тестирование

Для новой или изменённой бизнес-логики:

- используй Swift Testing;
- добавляй regression-тест для исправимого дефекта;
- проверяй основной сценарий, важные границы и переходы состояния;
- используй фиксированное время, in-memory persistence и fake-зависимости;
- не используй произвольный `sleep` для синхронизации.

Полные правила: `docs/WORKFLOW/TESTING.md`.

## Проверка изменений

Перед завершением выполни применимые проверки:

1. SwiftLint.
2. Сборка выбранной схемы для доступного iOS Simulator.
3. Swift Testing через `xcodebuild test`.
4. Проверка изменённых Preview через Xcode MCP и Canvas, если доступно.
5. Ручное прохождение изменённого сценария в Simulator.
6. Проверка `git diff` на случайные изменения, секреты и generated-файлы.

Правила Xcode и Simulator: `docs/WORKFLOW/XCODE_VALIDATION.md`.

Не утверждай, что проверка выполнена, если команда, Preview или сценарий фактически не запускались.

## Итоговый отчёт

После работы на русском языке сообщи:

1. Что изменено.
2. Какие файлы затронуты.
3. Какие проверки реально выполнены и их результат.
4. Что не удалось проверить и почему.
5. Какие риски, TODO или решения требуют подтверждения.
